# Analysis Plots Guide

Generated by `scripts/run_all_plots_test_round2.py`.
Each section describes one plot: what question it answers, what the axes show, and exactly where the data comes from.

---

## Group 01 — Validation

### `01_network_pdr_over_time` / `_merged`

**Question:** Does network packet delivery rate stay stable over the course of the experiment?

**Chart type:** Line chart — one line per run (or per protocol in the merged variant).

**X-axis:** Experiment time (minutes).
**Y-axis:** Sliding-window PDR = `window_delivered / (window_delivered + window_dropped)` within each reporting window.

**Data source:** `network_timeseries.csv` → column `window_pdr` (≥ 0 rows only).
In the merged variant each protocol's replicates are interpolated onto a common time grid and averaged with `np.nanmean`.

---

### `01_battery_ecdf` / `_merged`

**Question:** What is the distribution of UAV battery levels at the time of a charge request?

**Chart type:** Empirical CDF — one step-curve per run (or per protocol).

**X-axis:** Battery level at request time (%).
**Y-axis:** Cumulative fraction of requests.

**Data source:** `charge_events.csv` → column `request_battery` (sentinel -1 excluded).
In the merged variant, all replicates of a protocol are pooled before computing the ECDF.

---

## Group 02 — Per-Protocol Stats

### `02_charge_success_rate` / `_merged`

**Question:** What fraction of charge requests were successfully started (i.e., the UAV reached the dock)?

**Chart type:** Horizontal bar chart — one bar per run (or per protocol).

**X-axis:** Success rate ∈ [0, 1].
**Y-axis:** Protocol / run label.

**Calculation:** `STARTED_count / total_terminal_requests` where terminal outcomes are STARTED, REJECTED, DROPPED, TIMEOUT, PREEMPTED, ENERGY_DEPLETED.

**Data source (primary):** `charge_events.csv` → `outcome` column.
**Data source (fallback):** `experiment_summary.json` → `charging.success_rate`.

---

### `02_decision_latency` / `_merged`

**Question:** How long does the UGV take to make a charge scheduling decision after receiving a request?

**Chart type:** Box plot — one box per run (or per protocol, replicates pooled).

**X-axis:** Protocol / run label.
**Y-axis:** Decision latency (ms).

**Calculation:** `(decision_time − request_time) × 1000` ms, per charge request. Sentinel -1 excluded.

**Data source:** `charge_events.csv` → column `decision_latency_ms`.

---

### `02_effective_wait` / `_merged`

**Question:** How long does a UAV actually wait from sending a request until it starts charging (or times out)?

**Chart type:** Box plot.

**X-axis:** Protocol / run label.
**Y-axis:** Effective wait time (ms).

**Calculation:** `waiting_time_ms` if ≥ 0 (dock_start − request_time), otherwise `(terminal_time − request_time) × 1000` to capture timeouts and rejections. Sentinel -1 excluded.

**Data source:** `charge_events.csv` → column `effective_wait_ms`.

---

### `02_energy_recovered` / `_merged`

**Question:** How much energy (Wh) was actually transferred to a UAV per completed charging session?

**Chart type:** Box plot.

**X-axis:** Protocol / run label.
**Y-axis:** Energy recovered (Wh).

**Calculation (priority order):**
1. `charge_session_events.csv` DOCK_END rows → `energy_charged_wh` = `(end_battery − start_battery) × battery_capacity_wh / 100`. This is the most accurate source because it uses each UAV's actual battery capacity in Wh, correctly weighting CH UAVs (larger batteries) versus member UAVs.
2. If `energy_charged_wh` is all -1 (battery capacity not yet received): `(battery_after − battery_before) × battery_capacity_wh / 100` from the same DOCK_END rows.
3. Fallback for old-schema data: `charge_events.csv` → `energy_recovered_pct` (percentage points, not Wh).

In the merged variant all replicates of a protocol are pooled.

## Group 03 — Cross-Protocol Charging

### `03_charge_queue_length` / `_merged`

**Question:** How does the pending charge-request queue grow over time under each protocol?

**Chart type:** Line chart — one line per run (or mean line per protocol).

**X-axis:** Experiment time (minutes).
**Y-axis:** Total queue length (pending requests waiting for a decision or dock slot).

**Data source:** `charge_queue_timeseries.csv` → column `queue_length_total`.
Merged variant interpolates replicates to a common grid and plots the mean.

---

### `03_dock_utilization` / `_merged`

**Question:** How efficiently is the UGV dock being used over time?

**Chart type:** Line chart.

**X-axis:** Experiment time (minutes).
**Y-axis:** Dock utilisation fraction = `docks_occupied / total_docks` ∈ [0, 1].

**Data source:** `status_timeseries.csv` → columns `docks_occupied` and `total_docks`.

---

### `03_charge_outcome_breakdown` / `_merged`

**Question:** What is the breakdown of charge request outcomes (success, rejection, timeout, etc.) per protocol?

**Chart type:** Stacked bar chart — one bar per run (or per protocol in the merged variant).

**X-axis:** Protocol / run label.
**Y-axis:** Number of charge requests with each outcome.

**Outcomes and colours:**

| Outcome | Colour | Meaning |
|---------|--------|---------|
| STARTED | green | UAV successfully docked and started charging |
| REJECTED | red | UGV rejected the request (e.g., dock full, low priority) |
| DROPPED | orange | Request dropped in transit (routing failure) |
| TIMEOUT | purple | No decision received within the timeout window |
| PREEMPTED | brown | A higher-priority UAV displaced this one (**only shown for preemptive protocols**, i.e., those with `_p_` in their name) |
| ENERGY_DEPLETED | blue | UAV battery died before charging could start |

**Note on PREEMPTED:** Protocols without `_p_` in their name do not implement preemption. Any stray PREEMPTED counts in those runs are artefacts and are suppressed (set to 0) to avoid misleading the reader.

**Data source:** `charge_events.csv` → `outcome` column. Merged variant sums counts across all replicates.

---

### `03_dead_uav_cumulative` / `_merged`

**X-axis:** Experiment time (minutes).
**Y-axis:** Cumulative count of dead UAVs.

**Data source:** `death_events.csv` → `t_rel_s` column (one row per death event).

## Group 04 — Policy Radar

### `04_policy_radar` / `_merged`

**Question:** How do protocols compare across five key performance dimensions simultaneously?

**Chart type:** Radar / spider chart — one polygon per protocol.

**Axes (all normalised 0–1, higher = better):**

| Axis | Raw metric | Normalisation |
|------|-----------|---------------|
| PDR | `delivered / generated` | already ∈ [0,1] |
| Success rate | `STARTED / total` | already ∈ [0,1] |
| Low latency | mean `decision_latency_ms` | `1 − latency/100 000` (lower latency → higher score) |
| Energy recovered | mean `energy_recovered` Wh | `value / 100` |
| Survival | `survival_rate` from fleet stats | already ∈ [0,1] |

**Data source (primary):** `experiment_summary.json` → `network.by_category`, `charging`, `fleet`.
**Fallback:** CSVs (`qos_metrics.csv`, `charge_events.csv`) for runs without a summary JSON.

## Group 05 — Weather

### `05_pdr_vs_weather_regime` / `_merged`

**Question:** Does network packet delivery rate degrade under adverse weather conditions?

**Chart type (single):** Box plot — one box per weather regime, all protocols pooled.
**Chart type (merged):** Grouped bar chart — one bar group per regime, one bar per protocol.

**X-axis:** Weather regime label (e.g., `clear`, `rain`, `storm`).
**Y-axis:** Window PDR.

**Join logic:** `network_timeseries.csv` rows are matched to the nearest preceding `weather_timeseries.csv` row using a forward-fill asof merge on `t_rel_s`.

**Data sources:** `network_timeseries.csv` → `window_pdr`; `weather_timeseries.csv` → `regime`.

---

### `05_delay_vs_weather_regime` / `_merged`

**Question:** Does message end-to-end delay increase under adverse weather conditions?

**Chart type (single):** Box plot — one box per weather regime, all protocols pooled.
**Chart type (merged):** Grouped bar chart — one bar group per regime, one bar per protocol.

**X-axis:** Weather regime label.
**Y-axis:** E2E message delay (ms).

**Join logic:** Each message in `messages.csv` is matched to the weather regime active at its `creation_time_s` using a forward-fill asof merge on `weather_timeseries.csv` `t_rel_s`.

**Data sources:** `messages.csv` → `e2e_delay_ms` (delivered packets, sentinel -1 excluded); `weather_timeseries.csv` → `regime`.

## Group 06 — Network QoS & End-to-End Delay

### `06_qos_heatmap` / `_merged`

**Question:** Which message categories (DATA vs specific control message types) have the worst delivery rates, and does this differ across protocols?

**Chart type:** Heatmap — rows = message categories, columns = protocols, colour = PDR (red = low, green = high). Cell values are annotated.

**Colour scale:** `RdYlGn`, 0 (red) → 1 (green).

**Message categories:**

| Category label | `flow_type` | `control_type` |
|----------------|-------------|----------------|
| `DATA` | 0 | `""` |
| `CHARGE_DECISION` | 1 | `"CHARGE_DECISION"` |
| `RECOVERY_START` | 1 | `"RECOVERY_START"` |
| *(others as present)* | 1 | any non-empty string |

**Calculation:** For each run, take the **last** cumulative snapshot row per `(flow_type, control_type)` in `qos_metrics.csv` (the file is a growing timeseries — earlier rows are partial counts). Read `pdr = delivered / generated`.
In the merged variant, PDR values from all replicates of a protocol are averaged.

**Data source:** `qos_metrics.csv` → columns `flow_type`, `control_type`, `pdr`.

---

### `06_e2e_delay` / `_merged`

**Question:** What is the distribution of per-packet end-to-end latency across protocols?

**Chart type:** Box plot — one box per run (or per protocol in the merged variant).

**X-axis:** Protocol / run label.
**Y-axis:** E2E delay (ms).

**Calculation:** `(delivered_time − creation_time) × 1000` ms per delivered packet. Only packets with `delivered == "true"` and `e2e_delay_ms ≥ 0` are included.

**Data source:** `messages.csv` → column `e2e_delay_ms`.
In the merged variant all replicates of a protocol are pooled before plotting.

**Why this matters:** Unlike `decision_latency_ms` (which measures how fast the UGV makes a scheduling decision), `e2e_delay_ms` measures the full network propagation latency of every message type, showing how network conditions and protocol overhead translate into real communication lag.

## Protocol naming convention

Protocols containing `_p_` in their name (case-insensitive) are **preemptive** — the UGV can displace a lower-priority UAV mid-charge to serve a higher-priority one.  Protocols without `_p_` are **non-preemptive**.  The outcome breakdown plots use this convention to suppress the PREEMPTED bar for non-preemptive protocols.
